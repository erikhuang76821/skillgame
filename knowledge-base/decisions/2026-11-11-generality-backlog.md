## 1. 問題的來源：四層混在一起

| 層 | 內容 | 例子 | 通用程度 |
|---|---|---|---|
| 契約 | 輕量 skill game 的定義 | 同種子同輸入得同結果、可重播驗分、包體上限、不從 CDN 載入、排除機率玩法 | 通用 |
| 問題 | 每款都要回答的事 | 技巧是否決定結果、難度是否合理、簡單打法離上限多遠 | 通用 |
| 量法 | 怎麼量 | 種子 × 分級 bot、逐段難度指數、人性化 bot 的清怪率 | 依遊戲結構 |
| 門檻 | 量出來要多少 | 各條規則的數值 | 只有 1–3 款的證據 |

現在的規則常把後三層綁成一條，節點的產出與測試卡又把量法寫成檔名。修正方向是分開標示，各自有適用範圍。這個模型是討論中的整理，尚未被任何決策採用。

## 2. 現況盤點

### 可以用的

| 部分 | 現況 |
|---|---|
| 規則 | 集中在 `index/rules.json`，是數字的唯一來源；把關程式都從這裡取值 |
| 知識庫 | 每個 H2 一張卡，有 facet 標記與自動產生的索引 |
| 測試庫 | 每條規則都有對應的測試卡 |
| 資產庫 | 各遊戲登錄後彙整成中央索引 |
| 動態索引 | `context.mjs` 依節點與遊戲 profile 取出規則、知識、測試、資產 |
| 迴圈 | N0–N11；`loop.mjs` 的 status／next／gate／log；進度由紀錄檔重建；人工核准綁定檔案內容 |
| 把關 | pre-commit 跑 shared 測試、碰到的遊戲的測試與 audit、索引檢查 |

紙上試跑確認：階段順序、契約層、精髓七條與去隨機化的內容，對非動作類題目仍成立。

## 9. 不要做的事

- 不把單一遊戲量到的數字寫成跨遊戲的門檻。
- 不把討論中引用、未查證的判例或「業界判準」寫進知識庫。
- 不為還沒有人要做的遊戲形態預先建系統；用紙上試跑的故障清單決定要補什麼。

## 10. 執行紀錄

### 步驟 1：適用範圍與關卡漏洞（2026-11-11）

方案經 Codex 與 Gemini 兩輪討論後修正：補上「資料待補」怎麼傳到關卡、只有必過規則待補才擋關、先判明確不符再判缺值、三種結果也套用到既有的品類／渲染方式／來源。

| 項目 | 做了什麼 |
|---|---|
| profile | 新增布林欄位 `scriptedProgression`（同一局內是否有可量測的預設段落）；不是檢索用的 facet。三款既有遊戲都填 `true`：GateLane 有波次腳本、TwinStrike 有段落譜面、SwarmDuel 有敵潮時間表 |
| 規則 | 五條難度曲線規則的適用範圍從沒人檢查的 `difficulty` 改成 `scriptedProgression`；門檻不動 |
| 取用器 | 規則的適用判斷改成三種結果：適用、不適用、資料待補。待補的規則不進脈絡包，另列清單（規則、層級、缺哪個欄位） |
| 關卡 | 取用器有錯誤，或關卡要求的必過規則資料待補 → 結果是「無法驗證」。should 層級的待補只列出、不擋關 |
| 索引建置 | 規則的適用範圍只能用認得的欄位，否則建置失敗 |
| 測試 | 三種結果與優先序、未知欄位、合成 profile 不拿到曲線規則、缺值待補、關卡擋關、三款既有遊戲的規則與測試清單快照（`shared/tools/fixtures/`） |

驗證：三款既有遊戲在 N0–N11 的規則與測試清單前後相同；bootstrap 必讀表沒有變；shared 測試、GateLane 與 TwinStrike 的測試、三款 audit 的結果與改動前相同。

**還沒做到的**：非腳本的遊戲仍會被固定的文件與報告要求擋住（步驟 2）；卡片的缺值比對未改（步驟 6）；實驗資料夾裡的代理 profile 沒有填新欄位，現在重跑會看到曲線規則「資料待補」，和當時保存的輸出不同。

**副作用**：`GateLane/game.profile.json` 是 N0 的產出，加了一行之後 N0 的核准失效，N1、N2 也要重驗。

**Codex 審查程式後的修正**（同一批改動）

| 問題 | 修正 |
|---|---|
| profile 的值格式錯誤（例如來源填了非字串）會讓適用判斷當掉，關卡到不了「無法驗證」 | 格式錯誤的值視為沒填（資料待補），錯誤仍由 profile 驗證回報 |
| 適用範圍欄位的檢查只在索引建置時做；直接跑關卡仍會把拼錯的欄位當成適用 | 取用器每次組脈絡包都檢查，有錯就回報錯誤，關卡因此無法驗證 |
| 新測試用注入的脈絡包，沒走到真實路徑 | 補上走真實取用器的測試：欄位沒填、來源格式錯誤、適用範圍拼錯 |

**用乾淨副本驗證時另外發現並修掉的兩個既有錯誤**

- 在 Windows 的乾淨 checkout 上，bootstrap 必讀表永遠被判成過期：檔案被換成 CRLF，產生的表格是 LF。現在表格跟著檔案的換行格式。
- 關卡需要的 audit 測試因為缺檔而跑不了時，關卡會直接當掉。新遊戲在還沒有 sim 檔的節點就會碰到。現在這種情況是「未跑」，關卡結果是無法驗證。

驗證方式：用只含已進 git 檔案的副本加上這批改動跑 shared 測試，全部通過；改動前的 HEAD 在同樣的副本上有 2 個測試失敗。

### 步驟 2：文件與報告的依賴（2026-11-11）

| 項目 | 做了什麼 |
|---|---|
| 規則 | `RULE-GAME-DOCS` 的必備清單拆成兩組：一律必備，以及只在 `scriptedProgression` 為 true 時必備（`gdd/07_difficulty_curve.md`、`docs/playtest_report.md`）。`RULE-GAME-REPORTS`、`RULE-REPORT-FRESH` 只改措辭：有產生的報告才檢查。門檻不動 |
| audit | 讀遊戲的 profile 決定要不要第二組檔案。true：必備；false：不要求；沒填或沒有 profile：audit 不通過（資料待補），不預設成任何一邊 |
| 節點 | N5 的產出拆成 `produces`（技巧主導報告）與 `producesWhen.scriptedProgression`（試玩報告、難度文件）。旗標為 false 的遊戲在算缺檔與雜湊時不含第二組；沒填時照樣含，關卡另由「資料待補」擋下 |
| 範本 | `test/determinism.test.mjs` 的難度曲線測試讀 `<Game>/game.profile.json`，旗標為 false 就跳過；範本自己沒有 profile，照跑 |
| 說明文件 | 規格範本 §12、bootstrap 的完成條件與 §0 必讀表、skill 檢查表、知識庫 08 步驟 6b，都註明只適用有腳本進程的遊戲 |

驗證：

- 三款既有遊戲的 audit 結果逐列相同，只有 `gdd/07` 那一列的順序往後移。
- 有腳本進程的遊戲，N5 的雜湊和拆分前相同（測試直接比對），既有的關卡與核准紀錄不受影響。
- 三款遊戲在 N0–N11 的規則與測試清單和快照相同。
- 範本的曲線測試兩種情況都跑過：沒有 profile 時執行並通過；旗標為 false 時標示跳過。

**還沒做到的**：N5 的關卡仍只認現有的技巧佔比測試（步驟 3、4）；非腳本遊戲複製範本後，`tools/playtest.mjs`、`humanBots.mjs` 仍在資料夾裡，`RULE-TEMPLATE-LEFTOVER` 也仍把它們列為「要改寫」（should 層級，只是警告）；已經從範本複製出去的遊戲，測試檔是各自的副本，不會自動拿到這次的跳過判斷。

**Codex 指出、使用者同意後處理的兩項（2026-11-11）**
